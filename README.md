# Agent 运行架构对比：Foundry Hosted Agents、ACA 与 AKS

**面向 Azure 云架构师与互联网工程团队的研究结论。**

本研究将相同 Agent 业务分别运行在 Microsoft Foundry Hosted Agents、Azure Container Apps（ACA）和 Azure Kubernetes Service（AKS），回答两个实际问题：现有业务能否迁移，以及生产系统的运行责任应如何划分。

**核心结论：三种运行方式都能承载本研究的业务；选型的主要差异是运行治理与团队责任，而不是所选 Agent 框架能否接入。**

实验事实截至 **2026-10-10**，本版发布于 **2026-10-12**。这是一份经过整理的结果报告，不是云资源实时状态页。

## 一页结论

| 已确认结论 | 实验依据 | 对客户的意义 |
|---|---|---|
| 相同业务可以运行在三端 | Trading、多模态商品 RAG、工具会话探针共 9 个业务/runtime 组合均取得真实模型成功回执 | 可以保留业务逻辑，以适配层连接不同运行平台 |
| 所选五种编程模型均可接入 | 5 种 Python/.NET 实现 × 3 个 runtime，共 15 格真实工具与两轮会话验收 | 框架兼容性可以作为准入检查，而不是唯一选型标准 |
| 状态恢复需要明确的应用契约 | 三端完成 checkpoint 对照、协调服务重启、权限检查和连续 30 分钟无请求状态保留 | 持久状态、幂等和副作用处理应在设计阶段确定 |
| 企业私网与工作负载身份可以接通 | 三端完成共同私有 API 的 DNS/TLS 对照，以及共同 Vault/Storage 的身份允许与拒绝对照 | 需要验证数据面访问，不能只检查资源配置 |
| 版本升级与业务回滚可以落地 | 三端完成 V1 在途任务、V2 Trading/RAG、回滚后的 V1 Trading/RAG 验收 | 发布验收应覆盖业务结果和在途任务，而不止健康检查 |

表中的业务、会话和机制验证属于各自固定场景；样本分母与历史失败见[已验证结果](docs/validated-findings.md)。

## 如何选型

| 运行方式 | 建议采用的条件 | 团队需要重点承担的责任 |
|---|---|---|
| **ACA** | 已有容器化 API/后台任务，希望采用托管容器，且没有必须自管 Kubernetes 的需求 | 应用状态、任务账本、幂等、资源配置与发布策略 |
| **AKS** | 已具备 Kubernetes 平台团队，业务确实需要节点池、调度、网络策略或更细资源控制 | 集群与节点池治理、容量规划、工作负载策略，以及应用运行语义 |
| **Foundry Hosted Agents** | 以 Agent 服务和会话生命周期为中心，希望采用托管 Agent endpoint、identity 与 version | 业务编排、工具授权、业务幂等，以及所选协议下的状态与恢复契约 |

这是基于需求与责任边界的架构建议，不是性能或价格排名。详细判断见[架构选型建议](docs/architecture-decision.md)。
